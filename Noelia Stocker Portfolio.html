How I work

The same five steps, every time

  1. Measure the problem. Use SQL and KPIs to size it: volume, frequency, time cost, downstream impact.
  2. Find the most repeated task. Work done often, on a predictable trigger, gives the highest return.
  3. Learn what the systems can do. Read API docs, export schemas and field definitions, and compare them with what the team does by hand.
  4. Pick the right fix. Process redesign, automation, validation upstream, or bulk processing. Usually a mix.
  5. Ship, measure, document. Track before and after with the same KPIs, and write it down so the team can run it without me.

AI triage for support tickets that need QA

Problem
Another team asked whether QA could stay online later to cover urgent requests. With limited QA capacity, the real issue was that tickets needing QA were buried among dozens of others and reached us late in the day.
What I built
  • A script reads every unassigned conversation in the English support inbox.
  • A first AI agent summarises each conversation, suggests a next action and decides whether it needs QA & Delivery (delivery issues, near-late releases, release changes), with a reason.
  • A second AI agent (Claude) reviews that output against the same thread and corrects the verdict when needed.
  • Every ticket that needs QA triggers a Slack notification in a channel the team checks first thing in the morning.
Flow
  • Inbox
  • →
  • Summary + verdict
  • →
  • Second-agent review
  • →
  • Slack alert
Safeguard
Read-only. Nothing is drafted or sent to customers; the system only sorts, and a person handles every ticket.
Result
Urgent QA requests are handled at the start of the day instead of the end, without extending anyone's hours.

Failed-delivery monitoring

Problem
Customer Support kept escalating releases that missed their release date. In music distribution, a late release is one of the worst outcomes for an artist.
What I did
  • Used SQL to find the pattern: a wave of deliveries stuck in failed statuses after a system bug.
  • Handled the complaining customers first, then pulled every other affected release from the data and sent the IDs to Tech to re-trigger.
  • Built a scheduled report that scans all deliveries daily for failed statuses and posts them to a monitored Slack channel.
  • Logged recurring failure types so Tech could fix root causes.
Result
Over 1,000 assets rescued in the first clean-up. Today the monitor catches 5–10 failed deliveries every week, before customers notice.

Trust & Safety, and the AI-spam wave

Context
I built iMusician's Trust & Safety function: scope, processes, tooling and escalation paths, with SQL monitoring of payment and behaviour signals to flag risky accounts.

How the bulk-delivery query decides

A release goes out without a manual check only if every condition holds: the customer isn't flagged, the version name is clean, the audio fingerprint shows no conflict, and Content ID isn't involved.

WITH bundles_ready AS (
  SELECT DISTINCT b.id AS bundle_id, b.customer_id
  FROM delivery_bundles b
  LEFT JOIN releases r  ON b.id = r.delivery_bundle_id
  LEFT JOIN customers c ON c.id = b.customer_id
  WHERE b.status = 'ready'
    AND c.trust_level NOT IN ('fraudulent', 'suspicious')
    AND b.is_deleted = FALSE
    AND NOT EXISTS (
      SELECT 1 FROM release_names rn
      WHERE rn.release_id = r.id
        AND COALESCE(rn.version, '') ~ '\([^)]*\)')
),
track_analysis AS (
  SELECT b.bundle_id,
         SUM(COALESCE(f.score, 0))           AS fingerprint_score,
         ARRAY_AGG(DISTINCT t.content_id_status) AS content_id
  FROM bundles_ready b
  LEFT JOIN tracks t             ON b.bundle_id = t.bundle_id
  LEFT JOIN audio_fingerprints f ON t.id = f.track_id
  GROUP BY b.bundle_id
)
SELECT b.bundle_id, b.customer_id
FROM bundles_ready b
JOIN track_analysis t ON b.bundle_id = t.bundle_id
WHERE t.fingerprint_score < 0
  AND t.content_id = '{false}';

Table and field names are generalised. The logic matches the production query.
